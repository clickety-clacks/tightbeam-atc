# Air Traffic Control — driving the view

A live 3D display of the running Tightbeam org: agents hang below a grid, work
items float above it and descend as evidence accumulates, and lines show turns
and obligations. It is driven by a small unauthenticated HTTP API, so any agent on the box
can point the human at something.

- **Page:** <http://127.0.0.1:8787/>
- **API base:** `http://127.0.0.1:8787/api`
- **Service:** `systemctl --user status tb-atc`
- **Feed:** the web root's `data.json`, regenerated by
  `tb-weather-watch` from `state.db` (read-only)

There is no authentication. It controls a display and nothing else. Do not put
anything on it you would not say out loud.

## Node ids

Use the ids the feed publishes, exactly as they appear:

- **Work items:** `wi_...` (the substrate's work item id)
- **Agents:** `s_...` (the session suffix, the same one `tightbeam list` shows)

`curl -s localhost:8787/data.json` gives you the current population if you need
to resolve a name to an id.

## What the human is looking at

```bash
curl -s localhost:8787/api/selection
# [{"id":"wi_5870f52e","type":"item","title":"FIX SPEC+IMPL — supervision liveness…"}]
```

`/api/state` returns the selection, all tags and the command sequence at once.
Selection is reported by the page every couple of seconds, so it is current to
within about that.

## Pointing at something

```bash
# frame one node, everything else fades
curl -s -X POST localhost:8787/api/focus -H 'content-type: application/json' \
  -d '{"id":"wi_5870f52e","mode":"single"}'

# frame it together with everything it connects to
curl -s -X POST localhost:8787/api/focus -H 'content-type: application/json' \
  -d '{"id":"wi_5870f52e","mode":"neighborhood"}'

# release the focus
curl -s -X POST localhost:8787/api/focus -H 'content-type: application/json' \
  -d '{"mode":"clear"}'
```

## Selecting, and fitting the camera to it

Selection is a set the human also edits by hand (`s` puts the page in brush
mode). Add to it rather than replacing it unless you mean to take it over.

```bash
curl -s -X POST localhost:8787/api/select -H 'content-type: application/json' \
  -d '{"add":["wi_5870f52e","wi_62ef32ae","s_fde9b2be"]}'
curl -s -X POST localhost:8787/api/select -H 'content-type: application/json' \
  -d '{"remove":["s_fde9b2be"]}'
curl -s -X POST localhost:8787/api/select -H 'content-type: application/json' \
  -d '{"clear":true}'

# fly to the selection; {"on":false} returns the camera to where it was
curl -s -X POST localhost:8787/api/fit -H 'content-type: application/json' -d '{"on":true}'
```

`fit` is a round trip: the first call remembers the camera, the second puts it
back, including the rotation it was doing.

## Narrowing the whole view

`/api/filter` ghosts everything except the ids you name and frames what is
left — the same display a human gets by typing in the search box, except the
box shows an "agent search" pill so they know it came from you. This is usually
better than selecting: it answers "show me only these" without touching what
they had selected.

```bash
curl -s -X POST localhost:8787/api/filter -H 'content-type: application/json' \
  -d '{"ids":["wi_1a2b3c4d","wi_5e6f7a8b","s_1234abcd"]}'

curl -s -X POST localhost:8787/api/filter -H 'content-type: application/json' \
  -d '{"clear":true}'
```

They can clear it themselves by emptying the search box, so a filter you leave
behind is a nuisance rather than a trap — but clear it anyway when done.

## Tags

A tag is a short label pinned above a node. Provenance is rendered: **agent**
tags draw blue, **user** tags draw amber (red on the light theme). Always file
yours as `agent` — `user` is what the human types into the page.

```bash
curl -s -X POST localhost:8787/api/tags -H 'content-type: application/json' -d '{
  "tags":[
    {"target":"wi_5870f52e","text":"review stale since Aug 11","source":"agent"},
    {"target":"wi_62ef32ae","text":"off-branch","source":"agent"}
  ]}'

curl -s localhost:8787/api/tags                       # read them all
curl -s -X DELETE localhost:8787/api/tags/t3          # remove one
curl -s -X DELETE localhost:8787/api/tags             # remove all
```

Text is capped at 80 characters and at most four tags render per node. Tags are
in memory only: they vanish on service restart, which is the right lifetime for
a pointing device.

## Working well with the human

**Say what you did.** The display changes under their hands; a tag or a focus
that arrives unannounced is confusing. Tell them what you tagged and why.

**Clean up after yourself.** Delete the tags you filed when the question they
answered is closed. `c` on the keyboard clears every tag, so a human can always
reset what you did — but do not make them.

**Do not fight for the camera.** If they are mid-investigation, focusing
somewhere else yanks the view away. Prefer tagging, which is passive, and focus
only when asked or when you have told them you are about to.

**Read before you write.** `/api/selection` tells you what they are already
looking at. Answering about that is usually more useful than choosing your own
subject.

## Checking it is alive

```bash
systemctl --user is-active tb-atc          # the page and API
curl -s localhost:8787/api/state           # should return JSON
pgrep -f tb-weather-watch                  # the snapshot generator
```

If the page shows "feed unavailable" the watcher is down, not the API. Restart
with `systemctl --user restart tb-atc` and relaunch the watcher with
`TB_WEATHER_OUT=<web root>/data.json tb-weather-watch &`.

In a browser console, `__atc.view`, `__atc.tags` and `__atc.data` expose the
page's current state read-only.
